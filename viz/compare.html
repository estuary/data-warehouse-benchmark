    How to read this chart

    Dot shape shows how the size behaved as sessions were added (absorbs, queues or rejects). The horizontal axis lists only the session counts the study ran (1, 5, 10, 20, 50 and 100 on join queries, and 1, 5, 10, 20 and 43 on scan queries, plus 0 for sizes that served none at this target). The levels are evenly spaced, so each step moves to the next level the study measured. Within a level, engines are offset sideways so that sizes with the same result stay visible. The list under the chart names the cheapest size at each level.

    How speed and cost change with size at this data volume

    One panel per engine, one point per compute size measured at a data volume of about 100 GB, left to right by list price. The blue line is how many times faster the size ran the suite than the engine's cheapest size, and the orange line is how many times as much that run cost. Where the blue line is above the orange one, the speed increased by more than the cost, and there is value in sizing up to achieve speedier responses. When the orange line is above the blue line, it is not cost-effective to increase warehouse size to achieve faster query response times.

    How to read this chart

    Suite time is summed over the queries every size of that engine completed at this volume, so a small size that skipped the hardest queries does not look fast. The table under the chart gives each size's completed count and the size of that shared set. An engine measured at only one size at this volume has no ladder, and its panel names the size that ran; each engine's own page says why. BigQuery on-demand pricing has no hourly rate, so it is left off the ladder.

    Which kinds of query, and which data, slow an engine down

    Which kinds of query each engine finds hard under load

    The time for each query pattern relative to that engine's typical query at the same size and session count, so 1× is that engine's baseline. Above 1× means the pattern took longer than that engine's average query. A line that rises with sessions slowed down faster than the engine's other queries as load increased. Each panel compares an engine with itself, so heights should not be compared across panels.

    How to read this chart

    One panel per engine, one line per pattern. The ratio is formed inside each cell (same data volume, compute size and session count), so engine speed and compute size divide out and the ratio can be pooled across sizes. Dot size is the number of compute sizes behind the median. A query can carry several tags, so the patterns overlap.

    Bottom line

    Does skewed data slow each engine down

    Each DSB query (skewed data) against its TPC-DS twin (uniform data, same query number). The bars are the single-user pass at the designated size; the panels are every size under load. A bar that extends left from the 0% line, or a point below the 1× line, means the skewed version ran faster.

    How to read this chart

    Each DSB query is compared with the TPC-DS query of the same number. For 74 of the 99 pairs the two ask for the same report and differ only in how the data is spread, so the ratio shows what skew alone does to the time. The other 25 read the returns tables, which DSB also makes larger. The single-user bars use the 74, as the report does; the under-load panels use every pair. In this study the skewed version usually ran faster, which is the opposite of what most readers expect. The study recorded this but did not test why it happens. In the under-load panels, each point needs at least 20 queries that finished in both versions; points with fewer are left out.

    Before you quote a number from this page

    • Latency is server-side time from each engine's own query history. Network time is excluded. Under load it is engine time, the engine's queue wait included, on every engine.
    • Every measurement is one unit of compute at one size, with automatic scaling off. Several engines add clusters or capacity under load in production.
    • Costs are at list price and are obtained three ways (measured, allocated, modeled). Treat small cost differences between engines as approximate. None of the costs are price quotes.
    • No engine was tuned. No clustering, distribution or sort keys, partitioning or hand-built statistics were applied anywhere. The method page lists every choice that shaped the results.
